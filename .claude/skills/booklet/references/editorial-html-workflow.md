# Editorial HTML workflow для лид-магнитов

Цель: делать не "PDF из Markdown", а брендированный мини-гайд: Markdown отвечает за смысл, HTML отвечает за визуальную подачу, PDF является финальным экспортом.

## Фазы

1. `content.md` — чистый текст, структура, ссылки, таблицы, промпты. Это единственный источник смысловых правок.
2. `output/[slug].html` — визуальный прототип с фирменными стилями из `brand.yaml`. Здесь согласуются обложка, сетка, ритм, карточки, CTA.
3. `output/.tmp/[slug]-raw.pdf` — временный несжатый экспорт утверждённого HTML. Не отдаётся пользователю.
4. `output/[slug].pdf` — финальный сжатый PDF. PDF напрямую не редактируется.
5. `output/.tmp/qa-preview/` — обязательный рендер всех страниц и `qa-report.md` после сборки PDF.

Если пользователь просит изменить факты, порядок, формулировки или CTA — править Markdown и пересобирать HTML. Если просит изменить визуал, отступы, цвета, колонтитулы — править HTML/CSS-генератор и пересобирать HTML.

## Бренд

Цвета, логотип и название берутся из `brand.yaml` — в CSS они приезжают
переменными, руками их в генераторе не задают. Ключи палитры:

| Ключ в brand.yaml | Роль | CSS-переменная |
|---|---|---|
| `primary` | фон обложки, логотип, активные элементы | `--primary` |
| `blue` | ссылки, подсветки, мягкий акцент | `--brand-blue` |
| `gray` | фон секций | `--bg2` |
| `text` | основной текст | `--text` |
| `white` | поверхности и карточки | `--surface` |
| `red` | предупреждения | `--alert` |
| `muted` | колонтитулы | подставляется в `@page` |

Градиент `blue -> primary` разрешён только для знака/логотипа. В страницах гайда использовать плоские заливки, тонкие линии, белые поверхности на фоне `gray`, синие акценты и крупную типографику.

Бренд-ассеты должны быть локальными внутри скила:

| Что | Путь |
|---|---|
| Логотип | `assets/brand/logo-horizontal.svg` |
| Montserrat | `assets/fonts/montserrat/` |
| Geist | `assets/fonts/geist-sans/` |
| Geist Mono | `assets/fonts/geist-mono/` |

HTML не должен зависеть от Google Fonts, внешних CDN или системных шрифтов конкретного компьютера. Шрифты берутся только из `assets/fonts/` скилла и вшиваются в HTML как data URI.

## Типографика

- H1 обложки: Montserrat `54px`, `font-weight: 800`, `line-height: .98`.
- H2 разделов: Montserrat `40px`, `font-weight: 800`, `line-height: 1.05`.
- H3: Montserrat `25px`, `font-weight: 750`, `line-height: 1.18`.
- Основной текст: Geist `16.5px`, `line-height: 1.64`.
- Таблицы и prompt/code-блоки: минимум `14px`.
- Код, промпты, технические команды: Geist Mono.
- Не делать документ "синим". Синий — акцент, основной текст чёрный.

## Обязательная структура HTML-гайда

1. Обложка:
   - логотип бренда в белой плашке;
   - крупный H1;
   - подзаголовок;
   - без списка разделов: содержание будет на следующей странице.
2. Содержание:
   - список основных `h2`-разделов;
   - короткие описания, если они есть в Markdown;
   - визуальные номера `01`, `02`, `03`.
3. Введение:
   - обещание результата;
   - ранний CTA на сервис клиента, если он есть.
4. Основные разделы:
   - каждый крупный раздел получает editorial-разделитель или визуальную шапку;
   - карточки, таблицы, prompt/code-блоки не должны разрываться между страницами.
5. Финал:
   - краткий итог;
   - следующие шаги;
   - повтор CTA.

## Компоненты

- `cover` — обложка с крупной типографикой.
- `toc` — содержание.
- `sectionDivider` — разделительная страница или крупная шапка раздела.
- `callout` — важная мысль / совет / CTA.
- `promptBox` — тёмный блок для промптов и команд.
- `termGrid` — сетка терминов: термин слева, объяснение справа.
- `checklist` — список действий.
- `dataTable` — таблица с читаемыми ячейками.
- `ctaPanel` — финальный блок действия.

## Правила Markdown для хорошего HTML

- Один `# H1` — название гайда.
- Первый `##` после H1 можно использовать как подзаголовок.
- Основные части оформлять через `## Часть 1: ...` или `## Раздел 1: ...`.
- Внутри частей использовать `###` для карточек/инструментов/шагов.
- Промпты и команды писать fenced code block: тройные backticks.
- Скриншоты и иллюстрации вставлять стандартным Markdown-синтаксисом:

```markdown
![Скриншот сервиса: что пользователь видит на первом экране](assets/screenshots/service-home.png "https://service.com")
```

Путь должен быть локальным и относительным к `content.md`. Title в кавычках станет адресом в верхней browser-панели. Если title не задан, alt-текст станет подписью под картинкой в PDF.

Для скриншотов сайтов использовать единый viewport `1440×760` и `fullPage: false`, чтобы все browser-frame блоки были одинаковыми по пропорциям.

- Важные мысли писать blockquote:

```markdown
> **Главная идея:** короткая мысль.
```

- CTA писать blockquote со ссылкой:

```markdown
> **Попробуйте в <Бренд>:** [<домен>](https://<домен>)
```

## QA HTML до PDF

Перед экспортом в PDF проверить:

- HTML открывается локально без внешних ассетов.
- В HTML есть `@font-face` на локальные шрифты из `assets/fonts/`.
- Локальные картинки из Markdown встроены в HTML и видны в PDF.
- Обложка не выглядит как обычная первая Markdown-страница.
- Есть содержание.
- Есть верхний/нижний колонтитул в print CSS.
- Нумерация страниц есть только в нижнем правом колонтитуле в формате `стр. X из Y`; верхний колонтитул не дублирует номер страницы.
- Заголовки не оторваны от первого абзаца, нет одиноких 1-2 строк сверху или снизу страницы.
- Скриншоты, таблицы, callout-блоки и prompt/code-блоки не разрываются посередине страницы.
- Итоговые строки вроде `Сложность клонирования...` не висят одни вверху следующей страницы.
- Финальный CTA-раздел (заголовок из `cta.platform_heading_prefix`) выглядит как намеренная страница и не разрезан между страницами.
- Финальная CTA-ссылка держится с CTA-текстом.
- Prompt/code-блоки читаются и не рвутся посередине.
- Ссылки кликабельны.
- Цвета соответствуют палитре из `brand.yaml`.
- Нет года в копирайте, если пользователь явно не попросил.

## QA PDF после экспорта

После каждой сборки PDF сначала сжимать сырой PDF:

```bash
uv run .claude/skills/booklet/scripts/compress_pdf.py \
  lead-magnet-projects/[slug]/output/.tmp/[slug]-raw.pdf \
  -o lead-magnet-projects/[slug]/output/[filename].pdf
```

Стандарт: `160 dpi`, `JPEGQ=84`. Финальный PDF должен быть уже сжатым. Не оставлять в `output/` временные варианты `*-raw.pdf`, `*-ebook.pdf`, `*-compressed.pdf`; все тестовые файлы класть в `output/.tmp/`.

После сжатия запускать QA финального PDF:

```bash
uv run .claude/skills/booklet/scripts/qa_pdf.py \
  lead-magnet-projects/[slug]/output/[filename].pdf \
  -o lead-magnet-projects/[slug]/output/.tmp/qa-preview
```

Скрипт создаёт:

- `output/.tmp/qa-preview/page-N.png` — PNG каждой страницы для визуальной проверки;
- `output/.tmp/qa-preview/qa-report.md` — отчёт по подозрительным переносам.

Если в `qa-report.md` есть `Errors`, не отдавать PDF пользователю. Сначала исправить HTML/CSS/Markdown, пересобрать PDF и снова запустить QA.

Даже если отчёт чистый, агент обязан открыть все PNG-страницы и проверить глазами:

- нет зависшей строки вверху страницы;
- нет 1-2 строк перед новым разделом;
- нет заголовка без первого абзаца;
- финальная CTA-страница выглядит намеренно;
- скриншоты, таблицы и callout-блоки не разорваны.
