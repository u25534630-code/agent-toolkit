# Настройка Битрикса

Портал: `bitrix.lovekuhnya.online`. Всё ниже делается один раз.

> **Битрикс подключать не обязательно.** Оставьте `BITRIX_WEBHOOK_URL` пустым —
> бот будет забирать отклики, понимать голосовые команды, вести Google-таблицу,
> напоминать о собеседованиях и считать статистику. Не будет только движения
> стадий в CRM. Подключить можно в любой момент позже, ничего не переделывая.

## 0. Кто может это сделать

Создать вебхук с правом `crm` может **только администратор портала**. Битрикс
ведёт себя неочевидно: обычному пользователю он позволяет выбрать галочки и
нажать «Сохранить», но права молча не применяет. Симптом — ошибка
`insufficient_scope` при любом запросе к CRM.

Проверить, администратор ли вы: в генераторе запросов выполнить метод `profile`
и посмотреть на поле `ADMIN`. `true` — можно продолжать, `false` — нужен тот, у
кого есть админский доступ.

Проверить, что права реально записались, — метод `scope` без параметров.
Правильный ответ:

```
"result":["crm","im","user"]
```

Пустой `[""]` означает, что права не применились. Повторять запросы к CRM
бессмысленно, пока здесь не появятся три слова.

### Что написать администратору

Если портал настраивает подрядчик, просить нужно сразу всё — иначе цикл
«попросили → сделали не то → попросили снова» растягивается на недели. Готовый
текст, скопировать целиком:

> Привет! Нужен входящий вебхук в Битриксе для интеграции с ботом по подбору
> персонала.
>
> **Создать должен администратор портала.** Обычному пользователю Битрикс даёт
> поставить галочки и нажать «Сохранить», но права молча не применяет — мы на
> этом уже потеряли время. Проверить себя можно методом `profile`: в ответе
> должно быть `"ADMIN":true`.
>
> *Разработчикам → Другое → Входящий вебхук*
>
> - Название: **Бот рекрутера**
> - Права: **CRM (crm)**, **Чат и уведомления (im)**, **Пользователи (user)**
> - После выбора прав обязательно **«Сохранить»** внизу страницы — ссылка
>   генерируется только после сохранения
> - Кнопку **«Перегенерировать» после этого не нажимать**: она сбрасывает
>   права, и всё придётся выбирать заново
>
> Проверка, что получилось: там же, в «Генераторе запросов», метод `scope`,
> кнопка «Выполнить». Должно ответить `"result":["crm","im","user"]`. Пустой
> ответ или `[""]` — права не сохранились.
>
> Заодно подскажите, пожалуйста, **номер воронки HR** (той, где стадии «Новое
> резюме → Первичный созвон → … → Стажировка»). Его видно в адресной строке
> канбана: `.../deal/kanban/category/7/` — нужна цифра.
>
> Ссылку пришлите, пожалуйста, **личным сообщением**: она работает как пароль,
> по ней можно читать и менять CRM без входа в портал.

## 1. Входящий вебхук

*Слева → Разработчикам → Другое → Входящий вебхук*

Порядок важен: **сначала права, потом «Сохранить»** — ссылка генерируется после
сохранения. Кнопку «Перегенерировать» лучше не трогать: она сбрасывает права.

Права поставить три, больше ничего не нужно:

| Галочка в списке | Идентификатор | Зачем |
|---|---|---|
| CRM | `crm` | сделки и контакты кандидатов, движение по стадиям |
| Чат и уведомления | `im` | уведомления о собеседованиях внутри Битрикса |
| Пользователи | `user` | подставить ответственного за сделку |

На части порталов вместо `user` в списке два пункта — `user_basic` и
`user_brief`. Тогда берите **`user_basic`**: `user_brief` отдаёт только имя без
идентификатора, назначить ответственного по нему нельзя.

Скопировать URL вида

```
https://bitrix.lovekuhnya.online/rest/1/xxxxxxxxxxxxxxxx/
```

и вписать в `backend/.env` как `BITRIX_WEBHOOK_URL`.

Вебхук работает от имени того пользователя, который его создал — все сделки и
дела будут числиться за ним. Если хотите, чтобы они были на конкретном
рекрутере, создавайте вебхук из-под его учётки.

## 2. Воронка HR и коды её стадий

Подбор в этом портале ведётся **Сделками** в отдельной воронке HR — не Лидами.
Воронка уже существует со стадиями «Новое резюме → Первичный созвон →
Тестовое задание → Собеседование → Стажировка → Кадровый резерв».

Ничего создавать не нужно, только узнать коды:

```bash
cd backend && python -m scripts.setup_bitrix --show-stages
```

Скрипт напечатает список воронок и стадии каждой. Найдите воронку HR, её номер
впишите в `BITRIX_DEAL_CATEGORY_ID`, а коды стадий — в переменные ниже.

| Переменная в `.env` | Стадия воронки HR |
|---|---|
| `BITRIX_DEAL_CATEGORY_ID` | номер воронки HR |
| `BITRIX_STAGE_NEW` | Новое резюме |
| `BITRIX_STAGE_CALLED` | Первичный созвон |
| `BITRIX_STAGE_TEST_TASK` | Тестовое задание |
| `BITRIX_STAGE_INTERVIEW` | Собеседование |
| `BITRIX_STAGE_INTERN` | Стажировка |
| `BITRIX_STAGE_RESERVE` | Кадровый резерв |
| `BITRIX_STAGE_HIRED` | успешная стадия — вышел на работу |
| `BITRIX_STAGE_REJECTED` | провальная стадия — не подходит |

Полный код стадии выглядит как `C7:EXECUTING`. В `.env` нужна часть **после
двоеточия** — `EXECUTING`; номер воронки бот подставит сам.

## 3. Пользовательские поля

```bash
python -m scripts.setup_bitrix --create-fields
```

Создаст в карточке сделки:

| Код | Подпись |
|---|---|
| `UF_CRM_RESUME_URL` | Ссылка на резюме |
| `UF_CRM_AGE` | Возраст |
| `UF_CRM_CITY` | Город |
| `UF_CRM_EXPERIENCE` | Опыт, лет |
| `UF_CRM_SALARY` | Ожидаемая ЗП |
| `UF_CRM_REJECT_REASON` | Причина отказа |
| `UF_CRM_VACANCY` | Вакансия |
| `UF_CRM_BRANCH` | Филиал (ЕКБ, ЧЛБ, ТЮМ) |

Существующие поля скрипт не трогает.

## 4. Убрать лишнее из карточки

Это то, что нельзя сделать через REST — пять минут руками, зато карточка
перестаёт быть простынёй на два экрана.

Откройте любую сделку воронки HR → шестерёнка в правом верхнем углу карточки →
*Настроить поля*. Оставьте только:

**Основное:** Название, Стадия, Контакт, Источник, Комментарий

**Наши поля:** все `UF_CRM_*` из таблицы выше

Скрыть (перетащить в «Скрытые» или снять галочку):

- Компания, Реквизиты
- Сумма и валюта, Товары
- Счета, Документы, Оплата
- Наблюдатели, Дата изменения
- Всё, что относится к продажам: «Повторная сделка», «Тип сделки»

Имеет смысл свернуть вкладки **Лента** и **Документы** — рекрутер работает из
Telegram, в Битрикс заходит только за историей.

## 5. Отключить роботов и бизнес-процессы

*CRM → Сделки → воронка HR → Роботы*

По воронке подбора роботов быть не должно. Иначе получится дублирование:
бот переводит стадию → срабатывает робот → отправляет письмо или ставит
задачу, о которой никто не просил. Особенно это касается автоматических
писем кандидату и постановки задач при смене стадии.

## 6. Проверка

С `DRY_RUN=true` в `.env` запустите бэкенд и напишите боту тестовую фразу.
В логах будет видно, какие именно поля и стадии он собирается записать —
сверьте с тем, что ожидаете, и только потом снимайте `DRY_RUN`.

## 7. Если Битрикс отвечает «Access denied»

Так выглядит отказ в правах на запись:

```
crm.deal.add: HTTP 400 — {"error_description":"Access denied."}
```

Права на вебхук (галочка CRM) и права пользователя **внутри** CRM — разные
вещи. Галочка разрешает вызывать методы, роль в CRM решает, можно ли
что-то создавать. Отказ приходит, когда закрыто второе.

**Проверить самому, не дожидаясь администратора:** `rights.bat` в папке
`backend`. Он спрашивает вебхук, кто за ним стоит, что тот может прочитать, и
предлагает создать одну проверочную сделку, которую сразу удаляет. В конце
пишет, какой из трёх случаев это — галочка вебхука, доступ к CRM целиком или
только запрет на добавление.

**То же руками.** *Разработчикам → Генератор запросов*:

1. Метод — `crm.deal.add`
2. Параметры: `fields[TITLE]` = `Проверка прав`, `fields[CATEGORY_ID]` —
   номер воронки HR (посмотреть: `python -m scripts.setup_bitrix --show-stages`)
3. «Выполнить»

Ответ `{"result": 8123}` — права есть, сделка создана; удалите её методом
`crm.deal.delete` с `id` из ответа. Ответ `Access denied` — прав нет, дальше
к администратору.

**Что чинит администратор.** Два места, проверять оба:

- в самом вебхуке галочки `crm`, `user`, `im` — стоят и **сохранены**
  (кнопка «Перегенерировать» их сбрасывает);
- *CRM → Настройки → Права доступа → Права доступа* — у роли, в которой
  состоит пользователь вебхука, «Добавление: Разрешено» для Сделок и
  Контактов.

Кто этот пользователь, показывает `check.bat`: вебхук работает от имени
того, кто его создал. Администратору портала CRM не отказывает никогда, так
что если в проверке он администратор — причина в галочках вебхука, а не
в ролях.

Отклики, не заведённые из-за отказа, не теряются: бот не сдвигает отметку
времени и заведёт их при следующем опросе, когда права появятся.
