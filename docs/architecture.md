# Архитектура

## Общая схема

```
                    ┌──────────────────────────┐
   hh.ru API ──────▶│                          │──────▶ Bitrix24 REST
  (отклики)         │       recruiter-bot      │        (сделки, стадии, дела)
                    │                          │
 Telegram  ◀───────▶│   FastAPI + aiogram 3    │──────▶ Google Sheets API
 (голос/текст)      │   + APScheduler          │        (2 вкладки)
                    │                          │
                    │        SQLite/PG         │──────▶ Anthropic API
                    └──────────────────────────┘        (claude-opus-5)
```

Один процесс: FastAPI держит вебхуки и health-check, aiogram — бота,
APScheduler — напоминания, поллинг откликов и вечерний отчёт. База —
SQLite на старте, PostgreSQL при росте (меняется одной строкой в конфиге).

## Поток данных

### 1. Отклик приходит с hh.ru

```
APScheduler (в часы HH_POLL_TIMES + при запуске)
  → GET /negotiations?status=response         список новых откликов
  → GET /resumes/{resume_id}                  полное резюме (доступно работодателю
                                              по откликнувшемуся кандидату)
  → нормализация в Candidate
  → crm.contact.add + crm.deal.add            воронка HR, стадия «Новое резюме»
  → запись в БД (hh_negotiation_id — ключ идемпотентности)
  → сообщение в Telegram: «4 новых отклика»
```

Идемпотентность: `hh_negotiation_id` уникален в БД. Повторный поллинг того же
отклика не создаёт вторую сделку.

### 2. Рекрутер отчитывается о звонке

```
Голосовое в ТГ
  → скачиваем ogg/opus
  → faster-whisper (ru) → текст
  → Claude Opus 5, structured outputs → Command {action, candidate_ref, ...}
  → резолвим кандидата по фамилии среди активных
  → показываем предпросмотр с кнопками [Подтвердить] [Отменить]
  → выполняем: Битрикс + Sheets + напоминания
```

Текстовое сообщение идёт тем же путём, минуя расшифровку.

### 3. Вечерний отчёт

```
APScheduler (19:00 по МСК, будни)
  → агрегируем CallLog за сегодня
  → сводка в Telegram
```

## Модель кандидата и стадии

Одна сущность `Candidate` в нашей БД связывает три системы:

| Поле | Источник |
|---|---|
| `hh_negotiation_id`, `hh_resume_id`, `resume_url` | hh.ru |
| `bitrix_deal_id`, `bitrix_contact_id` | Битрикс |
| `sheet_row_tracking`, `sheet_row_intern` | Google Sheets |
| `status`, `reject_reason`, `interview_at` | наш процесс |

Стадии и как они ложатся на Битрикс:

Подбор в портале ведётся **Сделками** в отдельной воронке HR, а не Лидами.
Кандидат в Битриксе — это пара «контакт + сделка», как в существующих карточках.

| Наш статус | Стадия воронки HR | Что происходит ещё |
|---|---|---|
| `new` | Новое резюме | — |
| `called` | Первичный созвон | пишем в CallLog |
| `no_answer` | Первичный созвон | напоминание перезвонить |
| `test_task` | Тестовое задание | — |
| `interview_scheduled` | Собеседование | строка в «отслеживание проходящих», 2 напоминания |
| `interview_passed` | Стажировка | строка в «Стажеры» |
| `reserve` | Кадровый резерв | не отказ — к человеку можно вернуться |
| `hired` | успешная стадия | финал |
| `rejected` | провальная стадия (+ причина) | финал |

Номер воронки и коды стадий смотрит `scripts/setup_bitrix.py --show-stages` и
прописываются в `.env` — жёстко в коде их нет. Полный код стадии выглядит как
`C7:EXECUTING`; префикс с номером воронки клиент подставляет сам.

## Битрикс: что убрать из карточки

Задача «убрать в битриксе ненужные функции» решается настройкой, не кодом.
Рекомендуемый минимум полей в карточке сделки:

Оставить: `TITLE`, `STAGE_ID`, `CONTACT_ID`, `SOURCE_ID`, `COMMENTS` +
пользовательские `UF_CRM_RESUME_URL`, `UF_CRM_AGE`, `UF_CRM_CITY`,
`UF_CRM_EXPERIENCE`, `UF_CRM_SALARY`, `UF_CRM_REJECT_REASON`,
`UF_CRM_VACANCY`, `UF_CRM_BRANCH` (филиал: ЕКБ, ЧЛБ, ТЮМ).

Скрыть в настройках формы карточки: компания, реквизиты, валюта, сумма,
товары, счета, документы, лента, наблюдатели.
Роботы и бизнес-процессы по этой воронке отключить — их работу делает бот, иначе
получите дубли писем и задач.

Скрипт `scripts/setup_bitrix.py` создаёт недостающие пользовательские поля и
печатает их коды для `.env`. Скрытие полей формы через REST не делается — это
5 минут руками в интерфейсе, инструкция в `docs/bitrix_setup.md`.

## Google Sheets: схема вкладок

Заголовки читаются из первой строки листа и мапятся по названию — если у вас
колонки называются иначе или стоят в другом порядке, код подстроится сам.
Ожидаемые названия (регистр и лишние пробелы игнорируются):

Фактические колонки рабочей таблицы:

**«отслеживание проходящих»**

`п/п` · `Ф.И.О. кандидата` · `должность` · `город` · `Дата собеседования` ·
`Время` · *(без заголовка — кто проводит)* · `Обратная связь`

Дата и время собеседования разнесены по двум колонкам. Колонку «кто проводит»
бот не заполняет — он не знает, кто из коллег возьмёт собеседование.
Отдельной колонки «Статус» нет, поэтому результат дописывается в «Обратную связь».

**«Стажеры»**

`ФИО` · `Должность` · `CRM` · `Дата выхода на стажировку` ·
`С какого сайта сотрудник` · `Аттестация` · `Комментарий`

Лист разбит на блоки по месяцам («Январь 2026г») с отдельной нумерацией внутри
каждого. Бот дописывает строку в конец листа — внутри текущего месяца это верно,
но заголовок нового месяца он пока не создаёт.

Сопоставление идёт в два прохода: сначала точные совпадения заголовков, затем
вхождение подстроки, где выигрывает самый длинный синоним. Иначе «Дата
собеседования» досталась бы общему полю «дата». Ненайденная колонка просто не
заполняется, а при старте бот пишет в лог, какие поля не сопоставились.

## Разбор команд

Claude Opus 5 со structured outputs (`output_config.format`) — модель обязана
вернуть JSON по схеме, парсить свободный текст не нужно. Effort `low`:
задача простая, а латентность важна — рекрутер ждёт ответа между звонками.

Схема команды:

```python
class Command(BaseModel):
    action: Literal["reject", "schedule_interview", "interview_passed",
                    "no_answer", "note", "hired", "unknown"]
    candidate_ref: str | None      # как назвали кандидата
    reject_reason: str | None
    interview_at: str | None       # ISO 8601, уже разрешённый из «в четверг в 15:00»
    comment: str | None
    confidence: float
```

Текущие дата и время передаются в системном промпте, чтобы «в четверг в 15:00»
превращалось в конкретную дату. При `confidence < 0.7` или `action == "unknown"`
бот переспрашивает, а не гадает.

## Напоминания

Хранятся в БД (`Reminder`), при старте восстанавливаются в APScheduler — перезапуск
процесса не теряет напоминания. Два типа на собеседование:

- `confirm` — за 24 часа: «уточнить у Петровой, будет ли она на собесе завтра»;
- `interview` — за 1 час: «собес с Петровой Анной через час».

Отменяются автоматически при переводе кандидата в финальный статус.

## Безопасность

- Вебхук Битрикса и токены hh.ru — только в `.env`, в репозиторий не попадают.
- Бот отвечает только на `TELEGRAM_ALLOWED_USER_IDS` — чужой человек, нашедший
  бота, не получит доступ к базе кандидатов.
- Персональные данные кандидатов лежат в нашей БД в минимальном объёме
  (ФИО, телефон, ссылка на резюме) и нужны только для связи трёх систем.
- Голосовые файлы удаляются сразу после расшифровки.
